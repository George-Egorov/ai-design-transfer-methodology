# 响应性和适应性行为

BRIDGE 将响应行为作为一组声明的上下文和规则进行传输，而不是作为孤立的桌面/移动屏幕截图。

![Same-tree responsive behavior and an explicit structural transformation](../assets/diagrams/responsive-transformation.svg)

*默认为相同的逻辑树。不同的组合只有通过声明的保留意义和任务完成的转换才有效。*

## 准备好的根框架

为代表性设计环境创造根源。它们可能是 Figma 页面上的直接兄弟姐妹，或者组织在本地 Figma 部分下：

```text
Home [page=home] [route=/] [bp=1440] [view=default]
Home [page=home] [route=/] [bp=768] [view=default]
Home [page=home] [route=/] [bp=375] [view=default]
```

```text
Figma page
├─ Desktop variants                         // native Figma Section, organizer only
│  ├─ Home [page=home] [bp=1440] [view=default]
│  └─ Home [page=home] [bp=768] [view=default]
└─ Home [page=home] [bp=375] [view=default] // direct root is also valid
```

页面检查在发现根的同时遍历本机 Figma 部分，然后比较标记的根框架。它不会将组织者名称、顺序或嵌套视为产品结构，并且不会通过普通外部 `FRAME` 或 `GROUP` 来代替根。

`[bp]` 记录创作的帧宽度。它是证据和比较锚点；它本身并不规定媒体查询边界。将宽度/设备标签排除在子身份之外。

每个准备好的页面根目录在每个断点处都使用本机自动布局。框架构建的部分也使用自动布局，并且具有至少两个可见的有意义的流子级的通用容器也执行相同的操作。响应差异可能会改变自动布局方向、换行、间隙和大小；它们不能证明 `layoutMode=NONE` 或非资产 Figma GROUP 的合理性。

## 默认相同的逻辑树

在一页、视图、区域设置、主题、实验、角色和数据场景中，匹配根保留：

- 重要的逻辑要素和稳定的身份；
- 语义上的父/子关系；
- 内容和运行时数据含义；
- 动作、目标、形式名称和状态效果；
- 集合模式/基数规则而不是恰好适合一行的数字；
- 易于理解的姓名、关系、阅读顺序和任务完成情况；
- 内容/装饰/资产政策。

在不进行结构转型的情况下，以下内容可能会发生变化：

- 尺寸、间隙、填充、对齐和约束；
- 自动布局/弹性/网格方向和列数；
- 排版合同内的字体大小和自然环绕；
- 当阅读/焦点顺序保持正确时，同一语义父级内的同级视觉顺序；
- 声明可选呈现的可见性，而不用其他身份替换它；
- 定义策略时的粘性行为、溢出和几何。

“相同的树”意味着相同的逻辑/语义实体，而不是实现必须在视觉上隐藏重复的 DOM 节点。隐藏元素可能不会出现在渲染/可访问性树中，而其合约身份和可见性规则仍然可追踪。

## 不要使基数响应

网格从四列更改为两列仍然表示相同的结果集合。不要删除设计装置来填充最后一行：

```text
product-grid
  product-card-oak-chair
  product-card-wool-lamp
  product-card-steel-desk
  product-card-cork-stool
```

这些是设计夹具标识，而不是阵列位置。运行时身份来自稳定的产品记录密钥。不同的记录页面/窗口需要显式的分页/查询/数据场景规则。

## 视口和容器上下文

记录每个实现规则的驱动程序：

- **视口** 当整个应用程序外壳随着可用窗口而变化时；
- **容器** 当组件根据其自己分配的内联/块大小进行更改时；
- **功能** 当行为取决于输入、悬停、运动、颜色/对比度、安全区域或目标支持时；
- **内容/数据** 当内在内容或基数决定没有固定边界的布局时。

可重复使用的卡片网格通常应遵循其容器而不是占据设备。声明容器标识、轴、命名范围/条件和预期结果。目标可以使用 [CSS Containment specification](https://www.w3.org/TR/css-contain-3/#container-queries) 或等效的平台设施来实现这一点。

不要仅仅将断点边界推断为两个 Figma 框架之间的中点。设计者或实现所有者在测试过渡范围后声明它。

## 精确、阶梯和流体属性

对于每个属性，确定它是否：

1. **精确定位** — 准备好的帧值是接受点；
2. **步进** — 在声明的视口/容器/功能条件下切换；
3. **流动** — 在声明的范围内遵循最小/首选/最大规则；
4. **内在** — 遵循内容、换行、网格拟合或目标原生布局；
5. **通过例外修复** — 受规定的产品/平台原因限制。

流体契约记录属性、上下文/范围、最小值、首选关系、最大值、舍入/捕捉行为（如果可见）以及范围之外的行为。它不需要特定的 CSS 公式；Web 目标可以使用 [CSS Values and Units](https://www.w3.org/TR/css-values-4/) 中定义的机制，而其他目标本机映射相同的意图。

测试锚点、每个步骤的上方/下方、几个中间值、内容极限、缩放/回流和嵌套容器重用。“插值一切”并不是一个有效的政策。

## 宣布的结构转型

有时可用的演示文稿确实需要另一种组合：

- 比较表→贴有标签的披露卡；
- 持久侧边栏→模式/抽屉导航；
- 多面板编辑器→顺序步骤；
- 固定卷轴故事 → 静态有序部分；
- 图表+图例→小倍数+数据表。

这不是普通的断点差异。添加结构化 `responsive.transformations[]` 记录，其中包含：

- 转换 ID 和源/结果身份；
- 视口、容器、写入模式或功能条件；
- 完整的元素/字段/系列/场景映射；
- 语义和内容必须保持等效；
- 允许的省略以及省略细节的路径；
- 阅读、键盘和焦点顺序；
- 动作、验证、选择、滚动和状态转移；
- URL/历史记录/深层链接行为；
- 可访问的等效和简化运动后备；
- 当页面打开时条件发生变化时反向转换。

如果源标识没有结果映射，请记录其含义真正不适用的原因。“没有空间”是不够的。未声明的拓扑变化是合约漂移。

## 方向和写作模式

Locale 不足以描述布局方向。结构化上下文可以声明：

```json
{
  "direction": "rtl",
  "writingMode": "horizontal-tb"
}
```

当产品支持 `ltr` 和 `rtl`/双向应力夹具时，准备并测试它们。宣布：

- 整个构图是否镜像或仅逻辑流程发生变化；
- 逻辑开始/结束对齐和间距，而不是左/右假设；
- 哪些图标镜像（后退/前进、缩进），哪些图标不镜像（品牌标记、媒体控件、时钟、许多现实世界的对象）；
- 混合方向名称、电话号码、标识符、代码、日期和数值；
- 图表轴方向、类别顺序、图例、工具提示和正/负含义；
- 语义阅读和键盘顺序独立于视觉镜像；
- 涵盖长 RTL 副本和混合拉丁文/数字运行的屏幕截图或固定装置。

`方向` and `writingMode`除非工具具有本机属性，否则属于结构化上下文。不要为它们创建类似设备的平面标签。针对 Web 时，请遵循 [CSS Writing Modes](https://www.w3.org/TR/css-writing-modes-4/) 中的概念。

## 顺序和可见性

仅当保留逻辑阅读和焦点顺序时才允许视觉重新排序。不要使用布局顺序使键盘焦点不可预测地跳跃。响应式实施还必须在以下情况下定义焦点：

- 焦点元素变得隐藏；
- 侧边栏变成对话框；
- 表格成为披露信息；
- 状态打开时会发生调整大小/容器更改；
- 浏览器历史记录恢复不同的呈现方式。

重要内容可能不会仅仅因为视口很小而消失。可选内容可以通过映射的、可到达的呈现来公开或重新定位。

## 包装器、安全区域和溢出

在所有上下文中更喜欢相同的有意义的包装器。仅上下文包装器是声明的转换的一部分，或者是具有实际目的的显式结构异常，例如剪切、滚动包含、覆盖范围、语义分组或目标限制。

声明安全区域插入、为粘性/固定 UI 保留空间、视口单元策略、屏幕键盘行为以及相关的嵌套滚动所有权。焦点指示器、验证消息、工具提示和内容不得被意外剪切。

## 响应式审核门

仅当满足以下条件时，传输才准备就绪：

- 准备好的根具有明确的、匹配的上下文轴；
- 稳定的身份和含义默认匹配；
- 视口和容器驱动程序不会混淆；
- 步长边界和流体/内在规则涵盖中间尺寸；
- 每一次拓扑变化都有完整的变换映射；
- 数据基数和运行时标识不依赖于列或夹具顺序；
- LTR、RTL/双向、书写模式、缩放、长内容和本地化（如果适用）；
- 阅读顺序、焦点、动作、状态、历史和可访问性在每次变化中都存在；
- 不受支持的目标能力有一个自己的后备方案或明确的开放问题。
