# 采用 BRIDGE 和一个真实范围

不要从重命名库或迁移存档开始。在一个生产页面或一个新选定的部分上运行一个小型试点，让其设计者以外的其他人使用结果，并根据证据决定 BRIDGE 是否属于团队工作流程。

## 飞行员应该回答什么

只有回答了实际问题，试点才会成功：

- 其他人可以在不与作者通话的情况下识别页面、视图、断点、操作、目标和导出意图吗？
- BRIDGE 是否在实施开始前揭示了缺失的意图？
- 团队实际花费了多少准备和审查时间？
- 哪些发现阻碍了交接，哪些需要讨论，哪些是故意的例外？

我们的目标不是让一个展示文件看起来完美。目标是测试代表性工作的可重复移交。

## 选择一个有用的飞行员

使用一个活动页面，该页面足够小，可以在会话中查看，并且足够丰富，可以暴露真正的歧义。它应该包含：

- 至少两个断点；
- 至少一个具有真实目的地的链接或控制；
- 至少一个模式、状态、形式、锚点或其他目标；
- 结构重要的组件或部分；
- 内容加上装饰或导出的资产。

避免只为飞行员创建玩具屏幕。不要先迁移旧文件：未受影响的存档不会成为阻碍。

### 当主机产品是旧产品时

不要仅仅为了验证一个新部分而将页面标签修改到其他非 BRIDGE 文件上。创建或选择明确的边界，例如：

```text
Checkout summary [section=checkout-summary]
```

选择该根目录并运行 **检查所选部分**。对于响应证据，显式选择具有相同 `[section]` 值的两个或多个根；该命令仅比较那些选定的变体，而不会发现旧的同级变体。请勿将 `[page]`、`[bp]`、`[view]` 或 `[route]` 添加到该部分。单个选定的根声明一个请求的源上下文，并且不会仅仅因为不存在未请求的变体而失败。当整个部分是一个不透明的视觉对象时，所选根本身可能是 `[section=id] [asset]`，但嵌套在不同资产祖先下方的部分会被阻止，因为审核无法穿透该边界。

![Selected-section gate isolating one BRIDGE section inside a legacy page, with asset and instance boundaries and file/host-dependent references outside the selected roots deferred](../assets/diagrams/section-scope-gate.svg)

*仅检查选定的部分子树。不透明资产停止遍历，后代实例是受信任的原子边界，装饰层仍然被遍历，文件/主机解析是单独的检查。*

结果故意缩小：

- **准备就绪** — 对于声明的选定范围，没有任何阻塞结果、警告/TODO 或延迟检查；
- **部分** — 选定的源没有阻塞错误，但仍然有警告/TODO、选定的根 `INSTANCE`、无法区分的选定上下文或需要文件/主机查找的延迟引用；
- **阻塞** — 标记的边界丢失/无效或位于继承的不透明资产边界下方，选定的根是嵌套的或混合部分标识，或者阻塞发现仍然存在。

完整有效的 `http:`、`https:`、`mailto:` 和 `tel:` href 是经过创作解析的，不会导致部分；不完整或格式错误的外部 href 会阻止语法错误，而不是延迟。正常的后代实例是可信的原子边界，也不会降低Ready；只有本身就是 `INSTANCE` 的选定节根才是部分源证据。

就绪意味着**部分源已为声明的上下文做好准备**，而不是主机页面、路线、完整的响应集、旅程、实施、产品或 WCAG 一致性已准备就绪。仅解析选定根之外的文件/主机相关引用以及单独文件/集成检查中的主机放置。请参阅 [transfer contract](04-transfer-contract.md#selected-section-scope-inside-a-legacy-host) 和 [section-scope preflight](08-preflight-checklist.md#selected-section-profile-for-a-legacy-host)。

## 分配三个角色

|角色 |责任|
|--- |--- |
|设计师|准备选定的页面，并且在切换测试期间不进行任何解释。|
|开发者或审阅者 |读取文件、运行检查并记录每个问题或假设。|
|经理或流程所有者|定义成功阈值，保护试点范围，并决定是否扩大试点范围。|

一个人可以担任多个角色，但作者和测试切换的人不应该是同一个人。

## 分五个步骤运行试点

### 1. 记录基线

在更改文件之前，请要求接收者在没有作者的情况下检查该文件。记录：

- 识别页面及其断点所需的时间；
- 关于交互、目标、状态和资产的未解答的问题；
- 本来可以实现的假设；
- 设计师进行后续解释所花费的时间。

这是比较点，不是设计师的评分。

### 2. 仅添加缺失的意图

遵循 [designer quick start](00-designer-quick-start.md)。在 Figma 中保留几何图形、自动布局、组件数据和视觉样式。仅将稳定名称和 BRIDGE 标签用于 Figma 尚未表达的意图。

[BRIDGE Assistant plugin](https://www.figma.com/community/plugin/1654485530503673254/bridge) 可以应用通用标签、将控件连接到目标并显示文件映射。它不需要单独的 BRIDGE 帐户。

### 3.检查声明的范围

对于 BRIDGE 页面，选择页面根目录并运行 **检查页面**。对于上面的旧主机配置文件，选择标记的部分根或其明确选择的变体，然后运行 ​​*检查所选部分**。这两个司令部有单独的覆盖合同；不要将某个部分变成假页面以重复使用页面检查。

插件 0.9.3 覆盖快照记录了两个命令的精确发出规则联合：Page Check 报告 42 条目录规则（40 条自动规则和 2 条启发式规则），而 **Check selected section** 报告 26 条规则（24 条自动规则和 2 条启发式规则；20 条本地规则和 6 条选定变体）。由于范围重叠，计数不是累加的。当确切的范围很重要时，请查看 [Page Check coverage file](../validator/page-check-coverage.json) 或单独的 [selected-section coverage file](../validator/section-check-coverage.json)。

在任一检查期间，BRIDGE 仅监视声明的审计边界。同一 Figma 画布上的旧框架或其他 BRIDGE 页面中的后台活动不会使报告无效。如果被审计的根内部的层在读取时发生变化，插件会自动重复读取；如果相同的范围不断变化，它会停止并解释审核区域发生了变化，而不是 BRIDGE 编辑了文件。

完整的 [catalog contains 107 rules](../validator/rules.json)。当前插件覆盖范围之外的规则需要结构化合同检查、[designer checklist](17-designer-checklist.md)、启发式/手动审核或根据 [coverage manifest](../validator/methodology-coverage.json) 进行目标 QA。因此，干净的插件报告并不意味着每个目录规则都已被评估。页面检查还将放置的实例视为原子的；当其部分结构很重要时，单独审核可编辑源组件。

修复未解决的阻止程序。在上下文中讨论警告。记录有意的异常及其原因，而不是隐藏它们。

### 4. 在没有作者的情况下重复交接

将准备好的文件再次交给接收者。接收者应该能够找到：

1. 页面、视图和所需的断点；
2. 跨断点对应的元素；
3. 每个链接或动作及其目标；
4. 内容、装饰和可输出资产；
5. 任何记录在案的异常、转换、悬而未决的问题或改变实施的功能回退。

记录与基线相同的时间和问题计数。如果仍然需要口头提供核心答案，则合同是不完整的。

### 5. 根据结果决定

与团队一起对调查结果进行分类：

- **阻塞** - 实施否则需要猜测；
- **开放问题** - 未知是明确的、范围明确的、拥有的、分类为阻塞/非阻塞、分配审查点并给予安全后备；
- **接受例外** — 偏差是故意的并且有原因；
- **工作流程改进** — 可重复使用的约定、模板或清单更改。

仅当第二次切换足够清晰以证明准备成本合理时才扩展 BRIDGE。保留试点笔记；它们比一般性的“切换感觉更好”的说法更有用。

## 使用可衡量的成功标准

在试点之前设置阈值。一个实际的出发点是：

- 接收者在五分钟内回答五个交接问题，无需作者本人参与；
- 插件报告中不存在未解决的阻止结果；
- 每个已知的手动问题、异常或悬而未决的问题都有所有者、范围、阻止状态、审查点以及书面决定或安全后备；
- 记录前后澄清问题的数量和总交接时间；
- 开发人员可以在没有仅存在于聊天或会议中的私人上下文的情况下开始实施。

根据工作的复杂程度更改时间阈值，但保持测量和问题一致。

## 无需迁移项目即可推出

如果飞行员工作：

1. 将[designer checklist](17-designer-checklist.md)添加到设计审核中；
2. 在切换之前运行**检查页面**以获取页面范围或**检查所选部分**以获取隔离部分范围；
3. 在新页面和模板中重复使用经过验证的名称和标签；
4. 与其他实施决定在同一地点审查例外情况；
5.在一两个交付周期后评估另一个代表性页面。

当活动发生变化时，将 BRIDGE 应用到活动工作中。在每个历史文件都符合要求之前，无需重写存档、重命名整个组件库或块交付。

## 不该做什么

- 请勿标记尺寸、间距、颜色或 Figma 已存储的其他信息。
- 在第一次测量的切换之前不要重命名整个库。
- 不要将每个警告视为没有产品和技术背景的拦截器。
- 不要使用避免真实状态和交互的精美玩具锉刀。
- 不要将 42 页面检查规则或 26 选定部分规则呈现为完整 107 规则目录的自动化。
- 不要将 BRIDGE 变成偏离设计的单独规范。

## 成本、基础设施和数据

|问题 |当前答案 |
|--- |--- |
|许可和付款|该方法和该公共存储库已获得 MIT 许可；插件实现是私有的。插件版本 0.9.3 不要求付款，也没有付费 BRIDGE 帐户。|
|基础设施|不需要 BRIDGE 后端或团队服务器。已发布的插件声明没有网络访问权限。|
|存储的数据|语言和复制的目标本地存储在 Figma 客户端存储中。显式操作可以重命名选定的图层或将 BRIDGE 元数据附加到文档。没有任何内容发送到外部 BRIDGE 服务。|
|移民|无需迁移存档。从一个活动页面或一个明确选择的新部分开始，仅在工作流程证明有用的地方进行扩展。|

此存储库中的插件事实和覆盖率快照描述了版本 0.9.3。Figma 社区页面对于当前可安装的版本仍然具有权威性，因为发布是一个单独的手动步骤。插件实现存储库是私有的；公共方法存储库仍然是合同、覆盖范围和流程索赔的来源。

Figma 本身仍然是主机产品，并受您的组织已使用的工作空间计划和策略的约束。
