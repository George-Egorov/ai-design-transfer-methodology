# 交付前设计师清单

在将设计交给开发人员、人工智能代理或自动化实施工具之前，请使用这个简短的清单。目标很简单：另一个人应该在不与文件作者通话的情况下理解该文件。

如需严格审查，请使用 [full preflight checklist](08-preflight-checklist.md)。

## 先选择审核范围

对于完整的 BRIDGE 页面，请继续执行下面的编号页面清单。对于旧主机内的一个新部分，请使用此部分路径而不是创建页面元数据：

- [ ] 所选边界是具有 `[section=<stable-id>]` 的源根；它没有假的 `[page]`、`[bp]`、`[view]` 或 `[route]`。
- [ ] 一个根声明一个请求的上下文。响应式比较仅使用两个或多个具有相同节 ID 的显式选择的根。
- [ ] 所选子树满足下面适用的身份、结构、内容、资产/装饰、交互、组件和状态项。
- [ ] 所选根内的目标在本地解析；完整有效的 `http:`、`https:`、`mailto:` 和 `tel:` href 已编写解析，而格式错误的外部值则被阻止；仅延迟需要在根目录之外查找文件/主机的引用。
- [ ] 确切的 `[section=id] [asset]` 根可能是选定的不透明整个视觉效果，布局不适用；不同资产祖先下方的部分被阻止。`[decor]` 仍被遍历。选定的根 `INSTANCE` 是部分的；普通后代实例是受信任的原子边界，不会降低 Ready。
- [ ] **检查所选部分** 仅针对该部分源报告“就绪”、“部分”或“已阻止”；结果未显示为页面/产品/WCAG 就绪情况。

请参阅 [selected-section preflight profile](08-preflight-checklist.md#selected-section-profile-for-a-legacy-host)。仅页面检查表项目不在此审核范围内；不要将它们标记为通过。

## 1. 识别页面

- [ ] 每个根框架都有稳定的 `[page]`、`[bp]` 和 `[view]` 值。
- [ ] 根直接位于 Figma 页面上或仅由本机 Figma 部分组织；Figma 页面和根之间没有普通的外部 `FRAME`/`GROUP` 。
- [ ] `[route]` 仅在已知真实生产路线时才出现。
- [ ] 一页的断点保持相同的`[page]` 和`[view]`。

## 2. 保持断点逻辑上等价

- [ ] 重要元素存在于每个必需的断点处。
- [ ] 一个逻辑元素保留一个身份和一个逻辑父元素。
- [ ] 产品副本、价格、法律文本和操作不会悄然发生变化。
- [ ] 集合基数未调整以使网格看起来完整。

## 3. 分类部分

- [ ] 可重用页面部分来自 `Page Sections`。
- [ ] 普通接口组件保留在 `UI Kit` 中。
- [ ] 框架构建部分具有显式 `[section=...]`。
- [ ] `Page Sections` 中的实例不重复冗余部分标记。

## 4.使用稳定的身份

- [ ] 重要图层名称使用英文`kebab-case`。
- [ ] 名称不包含视口宽度或设备标签。
- [ ] 重复的设计实例具有不同的稳定层名称/`bridgeKey` 值；共享 `[item=...]` 值仅对角色/类型进行分类。
- [ ] 不同逻辑类型不会重复使用任何标识。

## 5. 在 Figma 中保留技术真相

- [ ] 图层名称不重复节点类型、自动布局、约束、剪辑或组件源。
- [ ] BRIDGE 标签仅表达 Figma 不知道的产品和传输意图。

## 6. 建立有意义的结构

- [ ] 每个页面根和框架构建部分都使用本机自动布局，即使有零个或一个子级。
- [ ] BRIDGE页面根永远不会携带`[asset]`；只有真正的后代视觉效果才能创造不透明的资产边界。
- [ ] 每个具有至少两个可见且有意义的直接流子级的通用内容容器都使用本机自动布局。
- [ ] 相关元素有一个有意义的框架/组件父级；在不透明的 `[asset]` 子树之外不存在 Figma `GROUP` 。
- [ ] 原始和叶子几何体是豁免的；后代 `[asset]` 根保留其父级自动布局中的一项。
- [ ] `[decor]` 仅标记确切的预期绝对视觉层，并且绝不借口自由形式的容器或组。
- [ ] 每个包装器都有真正的布局、分组、剪辑、表面或交互目的。
- [ ] 解释了仅一个断点的包装器。

## 7. 声明交互

- [ ] 导航使用 `[href]`。
- [ ] 接口更改使用 `[action]`。
- [ ] 草稿链接和控件使用 `[link]` 和 `[control]`，而不是虚假目的地。
- [ ] 每个模式、状态和表单操作都会解析为现有目标。

## 8. 准备真实的形式和内容

- [ ] 表单字段具有数据名称、标签和相关状态。
- [ ] 动态文本换行，无需手动换行。
- [ ] 固定文本高度有明确的原因和溢出行为。
- [ ] 长文本、本地化和真实 CMS 内容已经过测试。

## 9. 区分内容、装饰和资产

- [ ] 内容图像具有稳定的名称。
- [ ] 预期的绝对装饰视觉层在精确定位的节点上使用 `[decor]`。
- [ ] 整个导出的视觉效果使用 `[asset]`；复杂的装饰资产使用`[decor] [asset]`。
- [ ] 如果没有明确的原因，可编辑文本不会被光栅化。

## 10. 使状态明确

- [ ] 空、加载和错误页面状态使用 `[view]`。
- [ ] 组件状态存在于 `UI Kit` 变体或显式状态模型中。
- [ ] 隐藏的旧版本不是切换树的一部分。

## 11. 涵盖完整合同

- [ ] 运行时数据具有架构/密钥/源/格式以及加载、空、部分、过时、错误、脱机和适用的权限行为。
- [ ] 重要操作具有验证、待处理、失败、重试、取消、焦点、公告和历史记录的反应路径。
- [ ] 相同的树是响应式默认值；每个结构变化都有明确的语义/焦点/状态映射。
- [ ] 运动具有稳定的场景、反向/重新进入、缩减运动和不支持的后备。
- [ ] 实施目标和 QA 计划涵盖 WCAG 2.2 AA、键盘/焦点、缩放/回流以及支持的 RTL/双向上下文。
- [ ] 目标功能声明基本体验、媒体/数据预算、降级条件和后备。
- [ ] 每个未知/不受支持的项目都有范围、所有者、阻止状态、审核点、安全回退和状态。
- [ ] 每个偏差都有影响、缓解、证据、批准、所有者和审查日期。

## 最终测试

询问没有准备文件的人来识别页面、响应上下文和转换、可重用部分、交互和状态、数据/出处、动作回退、可访问性期望、目标限制、开放性问题、导出的视觉效果和偏差。如果任何答案仅存在于语音或聊天中，那么它就是一个未追踪的盲点，并且设计还没有准备好。
